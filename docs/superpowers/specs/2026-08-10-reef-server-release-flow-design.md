# Reef server release flow — design

**Date:** 2026-08-10
**Status:** approved, not yet implemented

## Problem

`reef-server` has no release process. There are no git tags in the repository, the version in
`reef-server/pyproject.toml` is edited by hand, `reef-server/CHANGELOG.md` does not exist, and the only image build
that happens anywhere is the per-pull-request `beta-<pr>` build in `reef-server-CI.yml`, which is discarded. Nothing
records what changed between two versions of the server, and nothing proves that a given version's image builds and
boots.

This design adds a [release-please](https://github.com/googleapis/release-please) flow that, on merge to `master`,
bumps the version, writes a changelog, creates a git tag and a GitHub release, and builds and smoke-tests the
corresponding Docker image. Publishing the image to Docker Hub is deliberately left out.

## Goals

1. Version bumps are derived from commit messages, not chosen by hand, and land in `reef-server/pyproject.toml`.
2. Every release produces a git tag, a GitHub release, and a `reef-server/CHANGELOG.md` entry.
3. Every release builds its Docker image and proves the image boots and reports the released version.
4. `reef-bundle` can be brought under the same flow later **with its own, independent version numbering**, without
   touching reef-server's version history or tag namespace.

## Non-goals

- Pushing the image to Docker Hub or any other registry. The release job builds and discards.
- Enabling release-please for `reef-bundle`. The configuration is shaped to accept it; it is not switched on.
- A commitlint or PR-title-lint workflow to enforce conventional commits.
- Changing which branch the existing CI workflows target. `master` stays the integration branch.

## Decisions

| Decision | Choice | Why |
|---|---|---|
| Release branch | `master` | Matches what `reef-server-CI.yml` and `reef-bundle-CI.yml` already target. Note the repository *default* branch is `main`, which forces an explicit `target-branch`. |
| release-please mode | Manifest (`release-please-config.json` + `.release-please-manifest.json`) | The only mode that gives per-component versions and per-component tags, which goal 4 requires. |
| Release type | `python` | Understands `[tool.poetry] version` in `pyproject.toml` and owns `CHANGELOG.md`. |
| Workflow layout | One workflow, two jobs | One run tells the whole story of one release. A registry push later is a step inside the job that already holds the version and the image. |
| Server version in the image | Baked in via `ARG`/`ENV` | `/api/v1/information` reports the truth without a deployer setting anything, and the smoke test can assert it. |
| Built image | Smoke-tested, then discarded | Proves the release is buildable and bootable at near-zero cost. No artifact storage or retention decision to make. |
| Token | Fine-grained PAT in `RELEASE_PLEASE_TOKEN` | GitHub triggers no workflows for a PR authored by the default `GITHUB_TOKEN`, so the release PR would get neither `reef-server-CI` nor `merge-gatekeeper`. |

### Rejected alternatives

**Simple (non-manifest) mode with a repo-wide version.** Fewer files, but one version for the whole repository:
a `reef-bundle`-only `feat:` would bump reef-server and cut a reef-server release. It also produces bare `v1.1.0`
tags, and once those exist there is no clean way to introduce a second component's tag namespace. Directly
incompatible with goal 4.

**A separate tag-triggered build workflow.** `reef-server-release.yml` cuts the release; a second workflow fires on
`push: tags: reef-server-v*`. This works now that a PAT creates the tag (a `GITHUB_TOKEN`-created tag triggers
nothing). It would allow rebuilding an old tag on demand, which is a speculative need, and it costs a second workflow
plus the loss of a single run that shows both the release and its image build.

## Architecture

Three new files, two edited, two documentation updates, and one file generated by the tool. Nothing under
`reef-server/reef_server/` is touched, so the test suite is unaffected.

```
release-please-config.json                       (new)
.release-please-manifest.json                    (new)
.github/workflows/reef-server-release.yml        (new)
reef-server/Dockerfile                           (2 lines added)
.github/workflows/reef-server-CI.yml             (1 line changed)
reef-server/README.md, CLAUDE.md                 (docs)
reef-server/CHANGELOG.md                         (created by release-please, never by hand)
```

### `release-please-config.json`

```json
{
  "$schema": "https://raw.githubusercontent.com/googleapis/release-please/main/schemas/config.json",
  "separate-pull-requests": true,
  "packages": {
    "reef-server": {
      "release-type": "python",
      "component": "reef-server",
      "include-component-in-tag": true
    }
  }
}
```

Three settings exist for goal 4 rather than for today's single component:

- `separate-pull-requests: true` — each component gets its own release PR and its own version. Without it,
  release-please bundles every component into one PR and their versions begin moving together.
- `include-component-in-tag: true` with an explicit `component` — tags read `reef-server-v1.1.0`, never bare
  `v1.1.0`. Bare tags are a one-way door: once `v1.0.1` exists, a second component cannot get a clean tag namespace.
- The `"reef-server"` key is the package **path**. `reef-bundle` joins as a sibling key with an identical block.

### `.release-please-manifest.json`

```json
{ "reef-server": "1.0.0" }
```

Seeded at the version already in `reef-server/pyproject.toml`, so the first release moves 1.0.0 → 1.0.1 for a `fix:`
or 1.1.0 for a `feat:`. release-please rewrites this file on every release, which is why the release workflow carries
no `paths:` filter (see below). Adding `reef-bundle` later is one more key; the two versions never interact.

### `.github/workflows/reef-server-release.yml`

```yaml
name: Reef server - Release

on:
  push:
    branches: [master]

# No `paths:` filter on purpose: release-please's own release commit rewrites the root
# .release-please-manifest.json, and a `reef-server/**` filter would hide that commit from this
# workflow. A commit touching only reef-bundle still starts this workflow, finds nothing
# releasable for reef-server, and exits.

concurrency:
  group: reef-server-release
  cancel-in-progress: false

jobs:
  release:
    name: Cut the release
    runs-on: ubuntu-latest
    permissions:
      contents: write
      pull-requests: write
    outputs:
      released: ${{ steps.release.outputs['reef-server--release_created'] }}
      version: ${{ steps.release.outputs['reef-server--version'] }}
      tag: ${{ steps.release.outputs['reef-server--tag_name'] }}
    steps:
      - uses: googleapis/release-please-action@v4
        id: release
        with:
          config-file: release-please-config.json
          manifest-file: .release-please-manifest.json
          # `target-branch` defaults to the repository default branch, which is `main` here.
          # Without this, release-please would read main's history and open PRs against main.
          target-branch: master
          # A PAT, not GITHUB_TOKEN: a pull request authored by GITHUB_TOKEN triggers no
          # workflows, so the release PR would run neither reef-server-CI nor merge-gatekeeper.
          token: ${{ secrets.RELEASE_PLEASE_TOKEN }}

  build-image:
    name: Build and smoke-test the release image
    needs: release
    if: needs.release.outputs.released == 'true'
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: reef-server
    env:
      VERSION: ${{ needs.release.outputs.version }}
      IMAGE: reef-server:${{ needs.release.outputs.version }}
    steps:
      # The triggering commit is the release commit — release-please tagged this exact SHA — so
      # the default checkout already carries the bumped pyproject.toml.
      - uses: actions/checkout@v4

      - name: Build the release image
        run: |
          docker build \
            --file Dockerfile \
            --build-arg REEF_SERVER_VERSION="$VERSION" \
            --tag "$IMAGE" \
            .

      - name: Smoke-test the image
        run: |
          docker run -d --name reef-smoke -e DAGS_VERSION=0.0.0-smoke -p 8080:8080 "$IMAGE"
          for _ in $(seq 30); do curl -fsS localhost:8080/api/v1/health && break; sleep 1; done
          curl -fsS localhost:8080/api/v1/health | grep -q '"healthy":true'
          curl -fsS localhost:8080/api/v1/information | grep -q "\"serverVersion\":\"$VERSION\""

      - name: Stop the container
        if: always()
        run: docker rm -f reef-smoke || true
```

`reef-server--release_created`, `reef-server--version`, and `reef-server--tag_name` follow manifest mode's
`<package path>--<output>` convention. The action also exposes an aggregate `releases_created`, which is shorter but
wrong for goal 4: once `reef-bundle` is managed, a bundle-only release sets it true and would build a reef-server
image for a version that did not change.

The smoke test asserts the version rather than merely a 200, because that assertion is what proves the `--build-arg`
reaches `/api/v1/information`. It sets `DAGS_VERSION` because that endpoint also requires the bundle version
(`service.py`, `describe_service`). It does not check `/api/v1/ready`: the base image ships no `dags.tar.gz`, so 503
there is correct behaviour, not a failure.

### `reef-server/Dockerfile`

Two lines, placed immediately before `EXPOSE` so that a version change does not invalidate the `poetry install`
layer above:

```dockerfile
ARG REEF_SERVER_VERSION
ENV REEF_SERVER_VERSION=${REEF_SERVER_VERSION}
```

No default value, deliberately. With no `--build-arg`, `ENV` is set to the empty string, and `describe_service` tests
it with `if not self._server_version` — so `/api/v1/information` still answers 500 exactly as it does today. A default
such as `dev` would replace today's honest "nobody told me my version" failure with a plausible lie.

### `.github/workflows/reef-server-CI.yml`

The existing build step gains `--build-arg REEF_SERVER_VERSION=${IMAGE_VERSION}`, where `IMAGE_VERSION` is already
defined as `beta-${{ github.event.pull_request.number }}`. Pull-request images then report their own identity too.
No trigger, branch filter, or job structure changes.

## Release lifecycle

1. A pull request merges to `master` with a conventional commit message touching `reef-server/**`.
2. `reef-server-release.yml` runs. release-please finds releasable commits under `reef-server/` and opens (or
   updates) a release pull request titled `chore(master): release reef-server 1.1.0`, containing the bumped
   `reef-server/pyproject.toml`, a new `reef-server/CHANGELOG.md` entry, and the updated
   `.release-please-manifest.json`. `released` is `false`, so no image is built.
3. Because a PAT authored that pull request, `reef-server-CI` and `merge-gatekeeper` run on it normally.
4. Merging the release pull request starts the workflow again. This time release-please creates the tag
   `reef-server-v1.1.0` and the GitHub release, and sets `reef-server--release_created` to `true`.
5. `build-image` runs, builds `reef-server:1.1.0` with the version baked in, asserts it boots and self-reports
   `1.1.0`, and discards it.

Version selection: `fix:` → patch, `feat:` → minor, `feat!:` or a `BREAKING CHANGE:` footer → major. Scoping is by
file path, not by commit scope — a commit only counts toward reef-server if it touches `reef-server/**`, so
`feat(reef-server):` is unnecessary.

## Failure modes

| Situation | Behaviour |
|---|---|
| No conventional commits since the last release | No release pull request, no tag, no build. Correct and silent. |
| Non-conventional commit messages (`Fix CI`, `test`) | Invisible to release-please. Nothing releases. All pre-existing history falls in this category, so the flow starts clean from the first conventional commit. |
| Pull requests squash-merged | The squash commit **title** is what release-please reads. A conventional PR title is therefore required; the individual commits inside are ignored. |
| `RELEASE_PLEASE_TOKEN` missing or expired | The `release` job fails on the API call. No tag, no partial release. |
| Image build or smoke test fails | The tag and GitHub release already exist — release-please creates them before `build-image` runs. The release is not rolled back; the failing run is the signal, and the fix ships as the next release. Accepted: reverting a published tag is worse than a red build against it. |
| Commit touches only `reef-bundle/**` | Workflow runs, release-please finds nothing for reef-server, exits without a pull request. |

## Prerequisites (manual, one time)

1. Create a fine-grained PAT on `TKul6/reef` with **Contents: read and write** and **Pull requests: read and write**.
   Store it as the repository secret `RELEASE_PLEASE_TOKEN`.
2. Land commits on `master` with conventional messages from now on.

## Verification

Locally, and fully:

- `poetry run pytest`, `poetry run ruff check`, `poetry run ruff format --check` from `reef-server/` — no source file
  changes, so this confirms nothing regressed.
- `docker build --build-arg REEF_SERVER_VERSION=9.9.9 -t reef-server:argtest .`, then run with
  `-e DAGS_VERSION=0.0.0-smoke` and confirm `/api/v1/information` reports `serverVersion: 9.9.9`. This is the same
  assertion the release job makes.
- A build with no `--build-arg`, confirming `/api/v1/information` still answers 500 and `/api/v1/health` still
  answers `{"healthy":true}`.
- `release-please-config.json` and `.release-please-manifest.json` validated as JSON against the published schema;
  both workflow files linted.

Only on GitHub, and only by the repository owner:

- With `RELEASE_PLEASE_TOKEN` in place, land one `fix:` commit under `reef-server/` on `master` and confirm a release
  pull request appears proposing 1.0.1. Merging it must produce the tag `reef-server-v1.0.1`, a GitHub release, and a
  green `build-image` job.

## Adding reef-bundle later

Add a sibling key to `release-please-config.json` (`"reef-bundle": { "release-type": "python", "component":
"reef-bundle", "include-component-in-tag": true }`), add `"reef-bundle": "1.0.0"` to the manifest, and add a
`reef-bundle-release.yml` modelled on the server's — its second job runs `poetry build` instead of `docker build`.
The two components then version, tag, and changelog completely independently: `reef-bundle-v2.3.0` can coexist with
`reef-server-v1.0.4`.
